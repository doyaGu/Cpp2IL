# P-CIL v1.1 Improvement Design

**Date**: 2026-03-25
**Status**: Design approved with targeted edits, pending implementation plan
**Revision**: R2 — incorporates major-revision feedback
**Scope**: Precision-oriented improvements to P-CIL v1 Formal Specification
**Input**: P-CIL_DESIGN_DECISIONS_FROM_EXISTING_IRS_2026-03-25.md + P-CIL_v1_Formal_Specification.md

## 1. Motivation

The P-CIL Design Decisions From Existing IRs document (2026-03-25) identified several capabilities that mainstream IR families provide but P-CIL v1 lacks. This design specifies how to close those gaps with maximum precision as the primary design goal.

### 1.1 Precision Dependency Chain

```
Value-level precision (value-flow)
    → Recovery state precision (four-state + contradictions)
        → Control flow completeness (implicit CF — deferred to v1.2)
            → Analysis contracts (taint/CPG)
```

Each layer depends on the preceding layer. This chain determines the implementation order.

### 1.2 Key Gaps Addressed

| # | Gap | Design Decisions Source | v1.1 Resolution |
|---|-----|----------------------|----------------|
| 1 | No explicit value-flow / SSA / def-use model | §4.2, §5.2 (Jimple/WALA lessons) | New Ch 4: Value-Flow Model |
| 2 | Recovery state model too simple | §7.1, §6.4 | Ch 3 rewrite: four-state + contradiction records |
| 3 | No unified call object schema | §5.3 | Ch 6 refactor: CallRecoveryObject |
| 4 | No static analysis contract | §5.6 | New Annex E |
| 5 | No CPG projection rules | §4.4 | New Annex F |
| 6 | Unity engine implicit control flow | §7.4 | Deferred to v1.2 |

| Decision | Choice | Rationale |

## 4. Ch 3: Enhanced Recovery Model

### 4.1 Four-State Model

Replaces v1's three-state + recognized-but-fallback:

```
verified > resolved > partial(strong | weak) > unresolved
```

| State | Semantics | Entry Condition | v1 Mapping |
|-------|-----------|-----------------|------------|
| **verified** | Independent cross-validation from multiple sources | >= 2 independent evidence source categories (symbol/metadata/pattern) converging, no unresolved contradictions | New (no v1 equivalent) |
| **resolved** | Single-source sufficient evidence | At least 1 Strong-level evidence source, no unresolved contradictions | v1 `resolved` |
| **partial** | Some evidence but incomplete | Has evidence but does not meet `resolved` conditions | v1 `partial` + v1 `recognized-but-fallback` |
| **unresolved** | Insufficient evidence | No meaningful evidence or domain cannot be determined | v1 `unresolved` |

**State transitions are driven by evidence structure, not confidence thresholds.** Confidence is computed (for diagnostics and progress measurement) but does not gate state transitions. The old confidence thresholds become informative "typical ranges", not normative gate conditions.

`verified` entry: >= 0.95 confidence is a SHOULD-level sanity check, not a MUST gate. The primary condition is structural: >= 2 independent evidence categories converging to the same conclusion.

### 4.2 Partial Sub-Bands

`partial` has two sub-classifications for lowering precision:

| Sub-classification | Condition | Lowering Permission |
|--------------------|-----------|-------------------|
| **partial-strong** | Has Strong-level evidence but some required fields are missing | Conservative CIL emission + placeholders |
| **partial-weak** | Only Moderate/Weak evidence, or only family identified | MUST NOT emit as resolved; emit fallback + diagnostics |

`family_recognized: true` is retained as an orthogonal marker (can appear in either sub-band) but is not the sole lowering decision factor.

### 4.3 Contradiction Records

New first-class data type:

```
ContradictionRecord {
    id:                unique identifier
    subject:           reference to the recovery object
    evidence_a:        EvidenceAnchor + interpretation_a
    evidence_b:        EvidenceAnchor + interpretation_b
    conflict_type:     "value" | "classification" | "state" | "carrier"
    resolution:        Resolved(chosen, reason) | Unresolved(reason)
    detection_context: string  -- recovery phase where detected
}
```

**Rules**:
- When evidence composition (v1 §3.4.3) detects contradiction, MUST create `ContradictionRecord` — not just mark `ambiguous: true`
- Resolved contradictions are retained in audit chain (`resolution = Resolved(...)`)
- Unresolved contradictions block state promotion to `resolved` or `verified`
- Contradiction records are properties of recovery objects, not a global table

**Resolution semantics**: When `resolution = Resolved(chosen, reason)`:
- `chosen` interpretation becomes the recovery object's primary interpretation
- The unchosen interpretation is preserved in the ContradictionRecord for audit
- The record is never deleted — it is permanent audit data

### 4.4 Ambiguity vs Contradiction

Both retained, orthogonal:
- **Ambiguity** = multiple candidate interpretations, cannot distinguish -> retain `candidates[]` + `preferred`
- **Contradiction** = evidence sources conflict with each other -> `ContradictionRecord`
- Ambiguity: "don't know which one". Contradiction: "two pieces of evidence say contradictory things"
- A recovery object MAY have both ambiguity and contradiction simultaneously

### 4.5 Lowering Impact

| State | Lowering Permission |
|-------|-------------------|
| verified | Highest-fidelity CIL emission; MAY omit diagnostic annotations |
| resolved | Direct CIL emission + evidence annotations |
| partial-strong | Conservative CIL + placeholders |
| partial-weak | Fallback + diagnostics; MUST NOT emit as resolved |
| unresolved | Effect-preserving fallback |

### 4.6 Deterministic Classification Algorithm

The following algorithm is the NORMATIVE classifier. It replaces all v1 confidence-threshold-based state gates.

```
ClassifyRecoveryState(evidence_set, contradictions):
  1. independent_categories = count_independent_categories(evidence_set)  -- see §4.7
     IF independent_categories >= 2 AND all_agree(evidence_set)
        AND NOT has_unresolved_contradictions(contradictions):
       RETURN verified

  2. IF has_strong_evidence(evidence_set)
        AND NOT has_unresolved_contradictions(contradictions):
       -- "strong" = symbol match, metadata match, or corroborated pattern
       IF all_required_fields_populated:
         RETURN resolved
       ELSE:
         RETURN partial-strong

  3. IF has_any_evidence(evidence_set):
       IF has_strong_evidence(evidence_set):
         -- strong evidence exists but contradictions block resolved
         RETURN partial-strong
       ELSE:
         RETURN partial-weak

  4. RETURN unresolved
```

**Key**: unresolved contradictions block promotion to `resolved` and `verified`, but do NOT collapse `partial-strong` into `partial-weak`. A recovery object with strong evidence AND an unresolved contradiction is `partial-strong`, not `partial-weak`.

**`chosen_target` selection** (replaces confidence-based ranking):
1. Rank candidates by evidence strength tier: strong > moderate > weak
2. Within same tier, rank by evidence count (more independent anchors = preferred)
3. Confidence score is used ONLY as final tiebreaker within same tier and count
4. When top candidates are in the same tier with same evidence count and no distinguishing evidence exists → mark `ambiguous: true` per Ch 3.6

**Deleted from v1.1**: The v1 `0.15` confidence gap rule for ambiguity is removed. Ambiguity is now triggered by evidence-structural indistinguishability, not numeric proximity.

### 4.7 Evidence Independence Model

**Independence matrix** for `verified` classification:

| Source A \ Source B | symbol | metadata | pattern | manual |
|---------------------|--------|----------|---------|--------|
| **symbol** | — | Independent (if symbol from linker, metadata from IL2CPP tables) | Independent | Conditional |
| **metadata** | Independent | — | Independent (if metadata from tables, pattern from code analysis) | Conditional |
| **pattern** | Independent | Conditional (if pattern derived from metadata → NOT independent) | — | Conditional |
| **manual** | Conditional | Conditional | Conditional | — |

**`manual` independence rule**: Manual evidence is independent from another source ONLY when the manual conclusion is anchored to a different root artifact (e.g., direct source code review vs. binary pattern matching) or comes from direct human inspection of the underlying data, NOT from reviewing another tool's output. A human confirming what a symbol-matching tool already reported is corroboration, not independent verification.

**Evidence anchor requirements**: Each `EvidenceAnchor` MUST carry:
- `source_category`: symbol | metadata | pattern | hybrid | manual
- `source_pipeline`: identifier of the tool/process that produced this evidence
- `root_artifact`: identifier of the underlying data artifact (e.g., "linker symbol table", "il2cpp metadata blob", "decompiled code slice", "manual source review")

Two evidence sources are independent iff `root_artifact` values are disjoint. Same `source_pipeline` with different `root_artifact` CAN be independent; same `root_artifact` with different `source_pipeline` is NOT independent.

### 4.8 Ripple: Confidence Becomes Auxiliary

All v1 sections that use confidence thresholds as normative gates (§3.5.2, §3.5.3, §5.6, §10.4) are rewritten:
- State transitions: governed by the deterministic classifier (§4.6)
- Confidence thresholds: retained as informative "typical ranges" only
- Composite confidence: `min(sub-confidences)` rule retained for diagnostics
- Composite state: the worst (least confident) state among sub-components. Quality ordering: `unresolved < partial-weak < partial-strong < resolved < verified`; composite takes the lowest.

## 5. Ch 4: Value-Flow Model (New Chapter)

### 5.1 Purpose

Provide an explicit, analysis-friendly value-flow model for P-CIL. Eliminate dependence on implicit host substrate def-use. Enable precise taint and dataflow analysis directly on P-CIL.

Design sources: Jimple (stack elimination + explicit values), WALA SSA IR (def-use + field sensitivity), MLIR (layering + explicit regions).

### 5.2 PValue

```
PValue {
    name:           unique identifier within function (%v0, %v1, ...)
    defining_op:    reference to the POperation that produces this value
    value_category: scalar | managed_ref | native_ptr | managed_valaddr |
                    rgctx_item | meta_slot_ref | unknown
    type_info:      RecoveredType | Unresolved<Type>
    evidence:       EvidenceAnchor[]
}
```

**Key properties**:
- **SSA form**: each PValue has exactly one definition point
- **Phi nodes**: control-flow merge points use `phi(v1, v2, ...)`
- **Stack-free**: no evaluation stack — all operation inputs/outputs are named values

**Phi + recovery state interaction**: `phi(%v1, %v2)` where inputs have different recovery states — output state = min(input states), consistent with Ch 3 composite propagation.

### 5.3 POperation

```
POperation {
    id:            unique identifier (OpId)
    opcode:        operation type
    inputs:        PValue[]
    output:        PValue?         -- None for void/side-effect-only ops
    side_effects:  SideEffect[]
    evidence:      EvidenceAnchor[]
}
```

**Recovery state is NOT a field on POperation.** Recovery state is carried in a sidecar `RecoveryIndex` on `PFunction` (see §5.10), breaking the `POperation <-> RecoveryObject` reference cycle. `CallRecoveryObject` and other typed views reference `POperation` by `op_id`, not by holding an instance.

```
RecoveryAttachment {
    state:          verified | resolved | partial-strong | partial-weak | unresolved
    contradictions: ContradictionRecord[]
    confidence:     float              -- auxiliary diagnostic
    view_kind:      call | value | check | meta | carrier | none
    view_ref:       CallRecoveryObject | ValueRecoveryObject | ... | None
}
```

Typed views (e.g., `CallRecoveryObject`) are projections accessed via `view_ref`. They reference back to the `POperation` by `op_id`, never by holding the instance. No circular references exist.

### 5.4 Opcode Taxonomy

| Category | Operations | Source Chapter |
|----------|-----------|---------------|
| Call | `pcil.call`, `pcil.callvirt`, `pcil.calli`, `pcil.newobj` | Ch 6 |
| Value | `pcil.box`, `pcil.unbox`, `pcil.isinst`, `pcil.castclass` | Ch 5 |
| Field | `pcil.ldfld`, `pcil.stfld`, `pcil.ldsfld`, `pcil.stsfld` | Ch 5 |
| Array | `pcil.newarr`, `pcil.ldelem`, `pcil.stelem`, `pcil.ldlen` | Ch 5 |
| Check | `pcil.nullcheck`, `pcil.boundscheck`, `pcil.div0check`, `pcil.overflow_check`, `pcil.arraystorecheck` | Ch 8 |
| Control | `pcil.br`, `pcil.brif`, `pcil.switch`, `pcil.ret`, `pcil.throw` | Ch 7 |
| Meta | `pcil.meta_init`, `pcil.rgctx_load`, `pcil.class_init` | Annex A |
| Phi | `pcil.phi` | This chapter |
| Literal | `pcil.const`, `pcil.ldstr`, `pcil.ldnull` | Ch 5 |
| Carrier | `pcil.carrier_create`, `pcil.carrier_extract` | Annex C |

### 5.5 Def-Use Chain

- **Def**: operation `op` defines value `%v` iff `op.output == %v`
- **Use**: operation `op` uses value `%v` iff `%v in op.inputs`
- Each PValue MUST have exactly one def (SSA property)
- Each PValue's uses MUST be dominated by its def
- Def-use chains MUST be traversable in both directions

### 5.6 Side Effect Model

```
SideEffect =
    | MemoryWrite { target: MemoryRegion, value: PValue }
    | MemoryRead  { source: MemoryRegion, result: PValue }
    | Exception   { type: RecoveredType?, condition: PValue? }
    | StateTransition { machine: StateMachineId, from: State, to: State }
```

```
MemoryRegion =
    | InstanceField     { base: PValue, field: FieldRef }
    | StaticField       { field: FieldRef }
    | ThreadStaticField { field: FieldRef }                  -- v1 Ch4 §4.4.8: distinct TLS path
    | ArrayElement      { base: PValue, index: PValue }
    | MetadataSlot      { slot_id: SlotId }                  -- Annex A/C.6: atomic init semantics
    | RGCTXSlot         { base: PValue, index: int }         -- Annex C.4: init/no_init policies
    | ByRefTarget       { ref: PValue, pointee: ByRefPointee }  -- managed ref dereference
    | HeapObject        { base: PValue }
    | Unknown

ByRefPointee =
    | LocalSlot     { local: PValue }
    | ArgumentSlot  { param_index: int }
    | FieldSlot     { base: PValue, field: FieldRef }        -- &obj.field
    | ElementSlot   { base: PValue, index: PValue }          -- &arr[i]
    | Opaque                                                  -- cannot determine target
```

`MemoryRegion` granularity directly determines field-sensitivity. `InstanceField` and `ArrayElement` level modeling enables field-sensitive taint analysis.

**Rationale for new regions**:
- `ThreadStaticField`: v1 already treats thread-static as an independent semantic path; different threads' TLS fields do not alias
- `MetadataSlot`: metadata globals have atomic-init semantics; must not alias with ordinary static fields
- `RGCTXSlot`: RGCTX arrays have distinct init/no_init access policies
- `ByRefTarget`: byref (`&T`) dereference must not be conflated with heap object access. `ByRefPointee` resolves the pointee to a concrete slot where possible; `Opaque` is the conservative fallback. This ensures `ldloca`/`ldarga` aliasing is precise.

### 5.7 Inter-Procedural Call Summary

```
CallSummary {
    method:            MethodRef
    param_effects:     Map<ParamIndex, Effect[]>    -- informative
    return_effect:     Effect?                       -- informative
    side_effects:      SideEffect[]                  -- informative
    state_effects:     StateTransition[]              -- informative
    recovery_state:    verified | resolved | partial-strong | partial-weak | unresolved
    valid_for_env:     PEnvironmentHash              -- summary only valid under this environment
}

Effect =
    | FlowsFrom { sources: (ParamIndex | "this" | "global" | "heap")[] }
    | Modifies  { target: MemoryRegion }
    | NoEffect
    | Unknown
```

`FlowsFrom` describes data-flow facts (where the value originates), not taint labels. Analysis engines layer taint semantics on top.

**Normative scope**: The `call_summary(method)` query contract (Annex E §7.5) is normative. The CallSummary field schema above (param_effects, return_effect, etc.) is **informative** — implementations SHOULD follow it but MAY use alternative representations.

**Rules**:
- Call summaries are optional — calls without summaries MUST use `unknown_effect` (conservative)
- Summary `recovery_state` follows the five-state model (§4.1, §4.2)
- Summaries MUST NOT claim precision beyond their recovery state
- A summary MUST only be reused under the same `PEnvironment` (matched by `valid_for_env` hash). Cross-environment reuse (different backend/generic-sharing/metadata-profile) is prohibited
- Summary composition, recursive SCC handling, invalidation, and versioning are deferred to v1.2

### 5.8 Graph Container Schema

P-CIL values and operations exist within a structured graph container:

```
PFunction {
    id:              unique identifier
    method_ref:      MethodRef
    params:          PValue[]           -- formal parameters as PValues
    return_type:     RecoveredType?
    entry_block:     BlockId            -- explicit entry point (not positional)
    blocks:          PBlock[]
    locals:          PValue[]           -- all locally-defined PValues
    recovery_index:  Map<OpId, RecoveryAttachment>  -- sidecar; breaks ref cycle
    call_summary:    CallSummary?       -- optional; informative (see §5.7)
    environment:     PEnvironment       -- see §10 minimal environment tuple
}

PBlock {
    id:              unique identifier (BlockId)
    operations:      POperation[]       -- ordered sequence within block
    successors:      PEdge[]            -- outgoing CFG edges (authoritative)
    handler_ref:     HandlerRef?        -- if this block is an EH handler entry
}
-- predecessors are a DERIVED VIEW: predecessors(B) = { E | E.target == B.id, E in all blocks' successors }
-- Implementations MUST ensure inverse(successors) is consistent; predecessors MUST NOT be stored independently.

PEdge {
    source:          BlockId
    target:          BlockId
    kind:            normal | branch_true | branch_false | switch_case(index) |
                     switch_default | exception | finally_exit |
                     filter_accept | filter_reject
    condition:       PValue?            -- for conditional branches
}

HandlerRef {
    kind:            catch | filter | finally | fault
    catch_type:      RecoveredType?     -- for catch handlers
    try_region:      BlockId[]          -- blocks comprising the protected region
}
```

`PBlock.handler_ref` connects EH structure to the block graph. A catch handler block has `handler_ref.kind = catch` and `handler_ref.catch_type` set. This mirrors ILAst's approach of making block/handler first-class objects.

### 5.9 Host Substrate Relationship

P-CIL value-flow is built from host substrate evidence:

```
Ghidra HighFunction varnodes / def-use
    -> P-CIL value-flow builder (implementation, not spec)
        -> PValue + POperation + def-use chains
```

- Spec defines **output format** (structural and semantic constraints)
- Spec does NOT define how to build from host substrate
- Spec MUST define graceful degradation: when host substrate def-use is incomplete, affected PValues get `value_category: unknown`

### 5.10 Carrier Operations Alignment with Annex C

| Annex C Lifecycle Stage | Ch 4 Value-Flow Representation |
|------------------------|-------------------------------|
| creation | `pcil.carrier_create` operation, produces PValue representing carrier |
| transfer | PValue flows through SSA (no special operation — natural value propagation) |
| consumption | `pcil.carrier_extract` operation, extracts field from carrier PValue |

Transfer requires no explicit operation — this is the natural semantics of SSA value flow. Annex C revision will state this explicitly.

## 6. Ch 6: Unified Call Semantics (Refactored)

### 6.1 CallRecoveryObject Schema

```
CallRecoveryObject {
    // === Value-flow interface (Ch 4) ===
    op_id:             OpId                -- references POperation by ID (no circular ref)
    receiver:          PValue?             -- this/obj (None for static)
    visible_args:      PValue[]            -- CIL-level visible parameters
    runtime_args:      PValue[]            -- IL2CPP-level actual parameters (incl. hidden)
    return_value:      PValue?             -- return (None for void)

    // === Protocol classification ===
    dispatch_family:   DispatchFamily
    family_evidence:   EvidenceAnchor[]

    // === Target resolution ===
    target_candidates: TargetCandidate[]
    chosen_target:     MethodRef?          -- None when unresolved
    target_evidence:   EvidenceAnchor[]

    // === Carrier dependencies ===
    carrier_deps:      CarrierBinding[]

    // === Recovery state (Ch 3) ===
    recovery_state:    verified | resolved | partial(strong|weak) | unresolved
    contradictions:    ContradictionRecord[]
    confidence:        float               -- auxiliary
}
```

### 6.2 DispatchFamily Enum

```
DispatchFamily =
    | DirectManaged       -- 5.4.1
    | Invoker             -- 5.4.2
    | Virtual             -- 5.4.3
    | GenericVirtual      -- 5.4.4
    | Interface           -- 5.4.5
    | GenericInterface    -- 5.4.6
    | Constrained         -- 5.4.7
    | DelegateInvoke      -- 5.4.8
    | Unclassified        -- cannot classify (renamed from v1 "Unresolved" to avoid confusion with recovery state)
```

### 6.3 CarrierBinding

```
CarrierBinding {
    carrier_type:    MethodInfo | RGCTXData | VirtualInvokeData | MetadataGlobal | Delegate
    role:            "hidden_param" | "dispatch_source" | "context_provider" | "invoke_stub"
    value:           PValue
    lifecycle_stage: creation | transfer | consumption
    recovery_state:  verified | resolved | partial(strong|weak) | unresolved
}
```

### 6.4 TargetCandidate

```
TargetCandidate {
    method:      MethodRef
    confidence:  float
    evidence:    EvidenceAnchor[]
    exclusion:   ExclusionReason?
}

ExclusionReason =
    | EvidenceContradicted { by: EvidenceAnchor }
    | SupersededBy { candidate: TargetCandidate }
    | InsufficientEvidence { reason: string }
```

`chosen_target` selection follows the deterministic algorithm in §4.6: rank by evidence strength tier, then evidence count, with confidence as final tiebreaker. When top candidates are in the same tier with same evidence count and no distinguishing evidence exists, Ch 3 ambiguity mechanism triggers.

### 6.5 Per-Family Constraints

Each family defines field constraints on the unified schema:

| Constraint | DirectManaged | Virtual | DelegateInvoke |
|-----------|--------------|---------|----------------|
| `receiver` | MUST for instance; MUST None for static | MUST | MUST (delegate object) |
| `runtime_args` tail | hidden MethodInfo (per C.3.2) | none (MethodInfo inside VirtualInvokeData) | method_code + method |
| `carrier_deps` required | MethodInfo (conditional) | VirtualInvokeData | Delegate carriers |
| `chosen_target` | statically known | runtime-resolved (slot + type) | runtime-resolved (stub + method) |

v1 §5.4.1-5.4.8 per-family descriptions are preserved but rewritten as:
1. Precondition -> unchanged
2. Evidence -> unchanged
3. Native signature -> maps to `runtime_args` layout
4. Carriers -> maps to `carrier_deps[]` required bindings
5. Post-state -> maps to `chosen_target` + lowering CIL instruction

### 6.6 Composite State Propagation

`recovery_state(Call) = min(recovery_state(chosen_target), recovery_state(carrier_deps[]))`. Consistent with Ch 3.

## 7. Annex E: Static Analysis Contract

### 7.1 Analysis Dimensions

| Dimension | P-CIL Guarantee | Requirement Level |
|-----------|----------------|-------------------|
| Flow-sensitive | CFG explicit, operations ordered | MUST |
| Path-sensitive | Branch conditions are explicit PValues | SHOULD |
| Field-sensitive | `MemoryRegion.InstanceField` level modeling | MUST |
| Context-sensitive | Via CallSummary; degrades to context-insensitive without | SHOULD |
| Object-sensitive | Via PValue SSA uniqueness (different allocation sites = different PValues) | MAY |
| Exception-sensitive | Exception edges explicit, ExceptionState tracked | MUST |

### 7.2 Dataflow Analysis Contract

**Forward analysis**: basic block reachability, POperation inputs/outputs explicit (SSA), side_effects explicit, CFG edges complete including exception edges.

**Backward analysis**: any PValue traceable to def (SSA); any MemoryWrite traceable to written value.

**Inter-procedural**: CallSummary provides propagation; without summary, MUST assume `unknown_effect`.

### 7.3 Taint Propagation Paths

| Propagation Type | P-CIL Representation |
|-----------------|---------------------|
| Direct assignment | `%v2 = pcil.op(%v1)` -> value-flow edge |
| Field store/load | `pcil.stfld` / `pcil.ldfld` -> MemoryRegion edge |
| Array store/load | `pcil.stelem` / `pcil.ldelem` -> MemoryRegion edge |
| Call propagation | CallSummary `FlowsFrom` relations |
| Carrier propagation | CarrierBinding value-flow |
| Exception propagation | throw PValue -> catch handler |
| Callback propagation | DelegateInvoke -> indirect call |

**Implicit flow** (e.g., `if(secret) x = 1`): MAY track; not required by default.

### 7.4 Recovery State Impact on Analysis Precision

| Recovery State | Available Information | Precision Impact |
|---------------|---------------------|-----------------|
| verified | Full value-flow + types + carriers | Highest |
| resolved | Full value-flow + types | High |
| partial-strong | Partial value-flow, missing fields = `Unknown` MemoryRegion | Conservative approximation |
| partial-weak | Family-level info only | Coarse approximation |
| unresolved | No semantic info | `unknown_effect`: assume arbitrary side effects |

Analysis MUST NOT assume no side effects for `partial-weak` or `unresolved` operations.

### 7.5 Analysis Query Interface

Semantic contracts (not API form):

| Query | Semantics |
|-------|-----------|
| `defs(v)` | Definition point of value v (exactly one, SSA) |
| `uses(v)` | All use points of value v |
| `reaching_defs(op, region)` | Reaching MemoryRegion definitions at operation op |
| `cfg_succs(block)` | Basic block successors (including exception edges) |
| `cfg_preds(block)` | Basic block predecessors |
| `call_summary(method)` | Inter-procedural summary |
| `carrier_at(call, type)` | Carrier binding at call site |

`reaching_defs(op, region)` precision depends on MemoryRegion specificity. For `InstanceField{base, field}`: precise definition set. For `Unknown` region: MUST conservatively return all possible memory write operations.

## 8. Annex F: CPG Projection Rules

### 8.1 Design Principles

- CPG is a consumer, not the authority (Design Decisions §3.5, §6.5)
- Standard CPG 1.1 layers use standard mappings
- P-CIL-specific information carried via HPG extension properties
- Projection is lossy and one-directional

### 8.2 Layer Structure

```
P-CIL recovery objects
    -> Standard CPG 1.1 projection    (CALL, IDENTIFIER, CFG, REACHING_DEF, ...)
    -> P-CIL extension properties     (recovery_state, confidence, evidence, ...)
    -> HPG overlay                    (CSL, SOGL, HLL)
```

### 8.3 Core Node Mapping

| P-CIL Concept | CPG Node | Key Property Mapping |
|---------------|---------|---------------------|
| Function | `METHOD` | `FULL_NAME` = recovered method ref |
| PValue (local) | `LOCAL` + `IDENTIFIER` | `NAME` = PValue.name, `TYPE_FULL_NAME` = type_info |
| PValue (literal) | `LITERAL` | `CODE` = value |
| PValue (param) | `METHOD_PARAMETER_IN` | `INDEX`, `TYPE_FULL_NAME` |
| POperation (call) | `CALL` | See §8.4 |
| POperation (field access) | `CALL` (operator) | `<operator>.fieldAccess` + `FIELD_IDENTIFIER` child |
| POperation (array access) | `CALL` (operator) | `<operator>.indexAccess` |
| POperation (check) | `CALL` | `NAME` = `pcil.nullcheck` etc. |
| POperation (phi) | Not projected | Expanded into `REACHING_DEF` edges |
| POperation (return) | `RETURN` | |
| Basic block | `BLOCK` | CFG edges |
| EH region | `CONTROL_STRUCTURE` | `CONTROL_STRUCTURE_TYPE = TRY` |

### 8.4 Call Node Projection

| CallRecoveryObject Field | CPG CALL Property | Mapping Rule |
|-------------------------|------------------|-------------|
| `chosen_target` | `METHOD_FULL_NAME` | MethodRef -> fully qualified; **empty string** when unresolved |
| (when unresolved) | `NAME` | MUST preserve: family name (e.g., `"<virtual dispatch>"`) > partial symbol > `"<unresolved>"` |
| (when unresolved) | `SIGNATURE` | MUST best-effort: `visible_args` type concatenation > `"<unknown>"` |
| `dispatch_family` | `DISPATCH_TYPE` | DirectManaged/Invoker -> `STATIC_DISPATCH`; all others -> `DYNAMIC_DISPATCH` |
| `visible_args[]` | `ARGUMENT` edges | Each visible arg -> child expression, `ARGUMENT_INDEX` from 1 |
| `receiver` | `RECEIVER` edge | Receiver PValue -> child, `ARGUMENT_INDEX` = 0 |
| `return_value` | `TYPE_FULL_NAME` | Return type |
| `runtime_args[]` | **Not projected** | IL2CPP hidden params not visible in CPG |

**Key**: `visible_args` (CIL-level) are projected; `runtime_args` (IL2CPP-level) are not. CPG consumers see recovered CIL semantics.

**Unresolved calls**: Per CPG 1.1 spec, when the exact callee cannot be resolved statically, `METHOD_FULL_NAME` may be empty, but `NAME` and `SIGNATURE` MUST still capture known call-site information.

### 8.5 Value-Flow -> PDG Projection

| P-CIL Concept | CPG Edge | Mapping |
|---------------|---------|---------|
| Def-use chain | `REACHING_DEF` | def -> use, `VARIABLE` = PValue.name |
| Phi node | `REACHING_DEF` (multiple) | Each phi input -> each phi use expanded |
| Control dependence | `CDG` | Auto-generated from CFG + dominators |
| Field-sensitive flow | `<operator>.fieldAccess` + `FIELD_IDENTIFIER` | `CANONICAL_NAME` = `<declaring_type>.<field_name>`; Joern's standard field-tracking handles field sensitivity |

### 8.6 Frontend vs Auto-Generated Element Boundary

| Element | Created By | Rationale |
|---------|-----------|-----------|
| `METHOD`, `CALL`, `IDENTIFIER`, `LITERAL`, `LOCAL`, `BLOCK`, `RETURN`, `CONTROL_STRUCTURE` nodes | P-CIL frontend MUST | Core semantic nodes |
| `METHOD_PARAMETER_IN`, `METHOD_RETURN` nodes | P-CIL frontend MUST | Formal parameters and return |
| `AST` edges | P-CIL frontend MUST | Explicit AST construction |
| `CFG` edges (normal + exception) | P-CIL frontend MUST | From PEdge; P-CIL owns precise CFG |
| `ARGUMENT` edges | P-CIL frontend MUST | From visible_args |
| `RECEIVER` edges | P-CIL frontend MUST | From receiver |
| `REACHING_DEF` edges | Post-pass MAY auto-generate | Can be derived from P-CIL def-use; or let Joern standard pass generate |
| `CDG` edges | Post-pass auto-generated | Standard CPG: from CFG + dominators |
| `DOMINATE` / `POST_DOMINATE` edges | Post-pass auto-generated | Standard CPG |
| `CALL` edges (method linking) | Post-pass auto-generated | Standard CPG: auto-linked from METHOD_FULL_NAME |
| `FILE`, `NAMESPACE`, `SOURCE_FILE` nodes/edges | Auto-generated | Standard CPG: from FILENAME data |

### 8.7 Exception Edge Projection

- Exception edges MUST be projected as standard `CFG` edges (taint analysis must cover exception paths)
- SHOULD add extension property `PCIL_CFG_EDGE_TYPE = "normal" | "exception"` for path-sensitive analysis
- Implementations that omit the extension property remain conformant (SHOULD, not MUST)

### 8.8 EH Structure Projection

| P-CIL EH Structure | CPG Projection |
|--------------------|---------------|
| try region | `CONTROL_STRUCTURE` with `CONTROL_STRUCTURE_TYPE = TRY`. Handler blocks are ordered AST children. |
| catch handler | Child `BLOCK` (or `UNKNOWN`) of the TRY node, with extension properties `PCIL_EH_KIND = "catch"` and `PCIL_CATCH_TYPE = <type full name>` |
| finally handler | Child `BLOCK` of the TRY node, with `PCIL_EH_KIND = "finally"` |
| fault handler | Child `BLOCK` of the TRY node, with `PCIL_EH_KIND = "fault"` |
| filter handler | Child `BLOCK` of the TRY node, with `PCIL_EH_KIND = "filter"` |
| throw | `CONTROL_STRUCTURE` with `CONTROL_STRUCTURE_TYPE = THROW` (schema-native). Exception operand is an AST child expression. `<operator>.throw` operator-style is an acceptable alternative for toolchains that prefer it. |

**Rationale**: CPG schema pre-defines `TRY` and `THROW` as control structure types. Catch/finally/fault/filter are not pre-defined, so they are expressed as handler blocks with extension properties. One `TRY` node represents the protected region; its handlers are ordered children distinguished by `PCIL_EH_KIND`.

### 8.9 P-CIL Extension Properties

| Property | Attached To | Type | Meaning |
|----------|-----------|------|---------|
| `PCIL_RECOVERY_STATE` | All nodes | enum | verified / resolved / partial-strong / partial-weak / unresolved |
| `PCIL_CONFIDENCE` | All nodes | float | Auxiliary confidence |
| `PCIL_DISPATCH_FAMILY` | CALL | enum | P-CIL protocol family (finer than DISPATCH_TYPE) |
| `PCIL_CARRIER_TYPES` | CALL | string[] | Participating carrier types |
| `PCIL_CONTRADICTIONS` | Nodes with contradictions | int | Contradiction count (detail requires P-CIL query) |
| `PCIL_EVIDENCE_SOURCES` | All nodes | string[] | Evidence source categories |
| `PCIL_EH_KIND` | CONTROL_STRUCTURE (handler blocks) | string | "catch" / "finally" / "fault" / "filter" |
| `PCIL_CATCH_TYPE` | CONTROL_STRUCTURE (catch handlers) | string | Caught exception type full name |
| `PCIL_CFG_EDGE_TYPE` | CFG edges | string | "normal" / "exception" (SHOULD level) |

Extension properties are informational. Standard CPG queries do not depend on them. P-CIL-aware analysis can use them for confidence-weighted analysis. Extensions MUST be registered via HPG schema extension mechanism (aligned with `CpgExtCodegen.scala`).

### 8.10 HPG Integration

| HPG Layer | Responsibility | P-CIL Relationship |
|-----------|--------------|-------------------|
| CSL (Code Semantics) | CIL semantic nodes | P-CIL standard projection directly serves CSL |
| SOGL (Static Object Graph) | Unity asset object graph | P-CIL does not project to SOGL; SOGL from AssetDumper |
| HLL (Hybrid Linkage) | Code <-> asset bridging | HLL connects CSL (from P-CIL projection) and SOGL |

### 8.11 Projection Quality by Recovery State

| Recovery State | CPG Projection Quality | Consumer Effect |
|---------------|----------------------|----------------|
| verified | Complete nodes + edges + types | Equivalent to hand-written CPG |
| resolved | Complete nodes + edges; types may be imperfect | High-quality analysis |
| partial-strong | Nodes exist but some properties empty/unknown | Analysis may over-approximate |
| partial-weak | Nodes exist, `METHOD_FULL_NAME` empty, `DISPATCH_TYPE` may be inaccurate | Analysis falls back to conservative |
| unresolved | `UNKNOWN` node or not projected | Analysis skips |

### 9.7 Ch 11: Lowering Contract (was Ch 10)

**Change level: MAJOR**

- §10.4 lowering obligations rewritten for four-state model
- Old confidence thresholds become informative reference
- Fidelity levels realigned:

| Fidelity | Recovery State | Output |
|----------|---------------|--------|
| Full | verified / resolved | Direct CIL |
| Conservative | partial-strong | CIL + placeholders |
| Diagnostic | partial-weak | Fallback + diagnostics |
| Opaque | unresolved | Intrinsic + diagnostics |

- Lowering input model: consumes POperation graph (not individual recovery objects)
- New §11.X: Phi Elimination and Stackification (see below)

**§11.X Phi Elimination and Stackification**:

**Phi elimination**:
- `pcil.phi` is a pre-lowering artifact; MUST be completely eliminated before CIL emission
- Standard SSA destruction: insert copy operations at end of each predecessor block assigning to the phi target local variable
- **Critical edge splitting**: MUST split critical edges (edge from block with multiple successors to block with multiple predecessors) before inserting phi copies. Without splitting, copies on shared edges would corrupt values for other successors.
- **Exception edge exception**: Phi copies MUST NOT be inserted on exception edges. ECMA-335 requires that exception handler entry occurs only via the exception mechanism, not via inline code. Phi values that arrive via exception edges MUST be resolved through landing-pad locals: the potentially-throwing operation stores to a local before the exception point; the handler reads from that local after entry.
- After phi elimination, the function degrades from SSA to local-variable form, then enters stackification.

**Stackification**:
- Convert named local variables to CIL evaluation stack operations
- MUST guarantee stack depth consistency at every join point (ECMA-335 verification requirement)
- **EH stack contracts** (per ECMA-335 III.1.7.5):
  - `catch` handler entry: stack depth = 1 (exception object on stack)
  - `filter` handler entry: stack depth = 1 (exception object on stack)
  - `finally` handler entry: stack depth = 0
  - `fault` handler entry: stack depth = 0
  - `endfilter`: consumes one `int32` decision value from stack
  - `leave` instruction: clears the evaluation stack entirely
- ISIL backend infrastructure (v1 §10.9) provides basis for stackification mechanics

**ByRef/address-taking preservation**:
- `ByRefTarget` MemoryRegion PValues MUST maintain reference semantics through lowering (`ldloca` / `ldarga`)
- SSA copy-propagation MUST NOT eliminate a byref value if the original address's lifetime does not cover all uses
- Lowering MUST ensure that locals whose address is taken (`ldloca`) are not register-allocated away by stackification
